Composite

También llamado objeto compuesto o árbol de objetos.

Organiza piezas en un árbol y deja que el cliente use ese árbol con la misma operación que usaría sobre una sola pieza.

01

El problema

Composite tiene sentido cuando el núcleo del sistema es un árbol. El caso clásico es un pedido: hay productos sueltos y cajas. Una caja guarda productos y también otras cajas. Esas cajas internas pueden guardar más productos o más cajas, sin un límite fijo de niveles.

La pregunta de negocio es simple: ¿cuánto sale el pedido? En el mostrador se abren las cajas y se suman los precios. En código, esa idea se vuelve incómoda: hay que conocer cada clase, cada nivel de anidación y cómo recorrer cada uno. Con dos niveles se puede escribir a mano. Con una profundidad que no se conoce de antemano, el cliente se llena de casos especiales.

Sin una operación común

El código que calcula el total tiene que preguntar el tipo en cada piso del árbol. Un nivel nuevo obliga a abrir este método otra vez.

// Cada nivel repite la misma pregunta.
decimal total = 0;
foreach (var item in pedido)
{
    if (item is Producto p)
        total += p.Valor;
    else if (item is Caja c)
    {
        total += c.Empaque;
        foreach (var interno in c.Contenido)
        {
            if (interno is Producto p2)
                total += p2.Valor;
            else if (interno is Caja c2)
            {
                // ¿Y si adentro hay otra caja?
            }
        }
    }
}

Qué se rompe

  • El cliente conoce las clases concretas.
  • La profundidad queda escrita en el código, no en los datos.
  • Un tipo nuevo (un sobre, un bundle, un combo) obliga a tocar todos los recorridos.

El árbol ya está en el dominio. El diseño todavía no lo reconoce.

02

La solución

Productos y cajas pasan a compartir una operación, por ejemplo Precio().

Hoja

El producto responde

Devuelve su propio precio. No tiene hijos a quienes preguntar.

Contenedor

La caja reparte

Pide Precio() a cada elemento, suma lo que vuelve y, si corresponde, agrega el empaque.

Recursión

El árbol se recorre solo

Si un hijo es otra caja, esa caja hace lo mismo con su contenido, hasta llegar a las hojas.

El cliente deja de inspeccionar el interior. Pide el precio de la raíz y espera un número. No necesita saber si esa raíz es un libro o un pedido de cuatro niveles.

// El cliente habla con la interfaz, no con las clases.
IComponente pedido = ArmarPedido();
decimal total = pedido.Precio();

La ventaja concreta: al invocar el método, cada objeto decide si responde o si pasa la pregunta hacia abajo.

03

Una analogía

Un ejército está organizado por niveles. La orden nace arriba y baja: ejército, división, brigada, pelotón, escuadrón, soldados. Quien manda no arma una lista de cada soldado. Cada nivel sabe a quién tiene que transmitirla.

  1. Ejército
  2. División
  3. Brigada
  4. Pelotón
  5. Escuadrón
  6. Soldados

En Composite pasa lo mismo con el mensaje Precio(), Dibujar() o Mover(): entra por la raíz y cada contenedor lo reenvía a sus hijos.

Las cuatro piezas

Cada hijo de la caja vuelve a ser un IComponente. Por eso el árbol puede crecer sin cambiar el cliente.

1. Componente

Declara las operaciones que tienen sentido tanto en una pieza simple como en un grupo. En el pedido, esa operación es calcular el precio.

2. Hoja

Es el extremo del árbol. No contiene a nadie, así que no delega: el libro conoce su precio y lo devuelve.

3. Contenedor

Guarda una lista de componentes. No le importa si un hijo es producto o caja. Al recibir la pregunta, recorre la lista, junta los resultados y devuelve el suyo.

4. Cliente

Trabaja siempre contra la interfaz. Por eso el mismo código sirve para un objeto suelto y para una estructura grande.

Dónde viven Agregar y Quitar

En la caja. La hoja no promete operaciones que no puede cumplir. Para armar el árbol, el código que compone tiene que saber que está hablando con un contenedor.

La otra variante

En la interfaz. Así se agregan hijos sin preguntar el tipo. El costo es que la hoja hereda métodos vacíos o que lanzan error. Esa decisión tensiona la segregación de interfaces: la comodidad del cliente contra un contrato más honesto.

05

En vivo: el pedido de la librería

El pedido es una caja. Adentro hay un libro, una caja de útiles y una mochila. La caja de útiles tiene su propio empaque. Antes de recorrer, calculá el total en voz alta.

El número es el precio si agregás un producto, y el costo de empaque si agregás una caja.

Cliente

pedido.Precio()

—

Todavía no se pidió el precio.

El árbol ya está armado. El cliente todavía no hizo la llamada.

    06

    El mismo ejemplo en C#

    La hoja devuelve un dato propio. El contenedor no suma precios a mano: le pide a cada hijo la misma operación. Si el hijo es otra caja, esa llamada vuelve a entrar en Caja.Precio().

    public interface IComponente
{
    string Nombre { get; }
    decimal Precio();
}

public sealed class Producto : IComponente
{
    public string Nombre { get; }
    private readonly decimal _precio;

    public Producto(string nombre, decimal precio)
    {
        Nombre = nombre;
        _precio = precio;
    }

    public decimal Precio() => _precio;
}

public sealed class Caja : IComponente
{
    private readonly List<IComponente> _hijos = new();

    public string Nombre { get; }
    public decimal Empaque { get; }

    public Caja(string nombre, decimal empaque)
    {
        Nombre = nombre;
        Empaque = empaque;
    }

    public void Agregar(IComponente hijo) => _hijos.Add(hijo);
    public void Quitar(IComponente hijo) => _hijos.Remove(hijo);

    public decimal Precio()
    {
        decimal suma = Empaque;
        foreach (IComponente hijo in _hijos)
            suma += hijo.Precio(); // el hijo puede ser otra caja
        return suma;
    }
}
    Otro caso: agrupar figuras

    El mismo esquema sirve en un editor. Un círculo se dibuja solo. Un grupo no dibuja trazos propios: pide Dibujar() y Mover() a cada figura, y alguna de esas figuras puede ser otro grupo.

    public interface IFigura
{
    void Mover(int dx, int dy);
    void Dibujar();
}

public sealed class Grupo : IFigura
{
    private readonly List<IFigura> _hijos = new();

    public void Agregar(IFigura figura) => _hijos.Add(figura);

    public void Mover(int dx, int dy)
    {
        foreach (IFigura hijo in _hijos)
            hijo.Mover(dx, dy);
    }

    public void Dibujar()
    {
        foreach (IFigura hijo in _hijos)
            hijo.Dibujar();
    }
}

    07

    Cómo implementarlo

    1. Confirmá que el dominio es un árbol. Separá elementos simples y contenedores. El contenedor tiene que poder guardar ambos.
    2. Declará la interfaz con operaciones que sirvan en los dos roles. Si un método solo lo entiende la hoja o solo el grupo, pensalo dos veces antes de subirlo al contrato común.
    3. Creá las hojas. Puede haber varias: producto, servicio, círculo, texto. Cada una resuelve la operación con sus propios datos.
    4. Creá el contenedor con una colección del tipo de la interfaz, no de una clase concreta. En la operación, delegá en los hijos y combiná lo que devuelven.
    5. Definí alta y baja de hijos. En esta clase viven en la caja. Si el armado del árbol tiene que ser uniforme para el cliente, se puede discutir subirlos a la interfaz y asumir el costo sobre las hojas.

    08

    Cuándo usarlo

    El modelo ya es un árbol

    Carpetas y archivos, menús con submenús, organigramas, figuras agrupadas, documentos con secciones, pedidos con empaques. El patrón aporta las dos piezas base: hoja y contenedor, con el mismo contrato.

    El cliente no debería distinguir

    Cuando el código que usa la estructura tiene que tratar igual a un elemento y a un grupo. La interfaz común evita una cadena de preguntas por tipo.

    A favor

    • Polimorfismo y recursión reemplazan un recorrido escrito a mano para cada nivel.
    • Un tipo nuevo de hoja entra sin reescribir al cliente ni al contenedor. El diseño queda abierto a la extensión.

    En contra

    • Si hoja y contenedor se parecen poco, la interfaz común se estira hasta volverse difícil de leer.
    • Forzar las mismas operaciones en los dos roles puede esconder métodos que solo uno de los dos puede cumplir.

    09

    Cómo se cruza con otros patrones

    Builder

    Puede construir el árbol por pasos, incluso llamándose a sí mismo cuando una parte es otro árbol.

    Chain of Responsibility

    Una hoja puede reenviar la petición a su padre, y ese padre al suyo, hasta la raíz.

    Iterator

    Recorre los nodos sin que el cliente escriba la recursión.

    Visitor

    Agrega una operación nueva sobre todo el árbol sin modificar cada clase de nodo.

    Flyweight

    Las hojas que se repiten pueden compartirse para ocupar menos memoria.

    Decorator

    También compone objetos. El decorator envuelve uno y le suma comportamiento. El composite agrupa varios y resume lo que devuelven. Se pueden combinar: decorar un nodo puntual del árbol.

    Prototype

    Clona un árbol ya armado en lugar de reconstruirlo pieza por pieza.

    10

    Para charlar

    1. Si aparece un sobre, que también puede contener productos y meterse dentro de una caja, ¿qué clase nueva hace falta y qué código no se toca?
    2. ¿Dónde dejarías Agregar: solo en la caja, o también en la interfaz? ¿Qué gana el cliente y qué pierde la hoja?
    3. El pedido ahora también tiene que informar el peso. ¿En qué tipo declarás la operación para no volver al recorrido con if?

    Idea para cerrar: una sola operación, dos formas de cumplirla. La hoja responde. El contenedor reparte la pregunta y combina las respuestas.
